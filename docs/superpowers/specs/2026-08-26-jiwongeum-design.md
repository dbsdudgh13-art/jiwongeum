# 지원금 모아 — 설계 문서

작성일: 2026-08-26

## 목표

Google AdSense로 수익을 내는 정보 사이트를 만든다. 네 가지 제약을 동시에 만족해야 한다.

1. 검색에 잘 노출될 것
2. AdSense 승인을 무난히 받을 것
3. 분야별로 나뉜 AI 에이전트들이 운영할 것
4. 구축·운영 비용이 들지 않을 것

## 주제 선정

정부·지자체 지원금 정보를 정리해 제공한다. 원자료는 공공데이터포털이 개방한
「행정안전부 대한민국 공공서비스(혜택) 정보」(데이터셋 15113968). 실측 10,957건,
JSON, 무료, 이용허락범위 제한 없음, 개발계정 10,000회/일.
엔드포인트는 `https://api.odcloud.kr/api/gov24/v3/serviceList`, 응답 필드명은 한글이다.
신청 가능(open) 10,504건, 종료 453건.

이 주제를 고른 이유:

- 원자료가 유일하고 공개되어 있어, 가공한 페이지가 중복 콘텐츠가 되지 않는다.
- 검색 수요가 꾸준하고 계절성이 적다.
- 에이전트가 반복 생산할 수 있는 형태의 콘텐츠다.

한계도 명확하다. 지원금 키워드의 CPC는 낮은 편이라 수익은 클릭 단가가 아니라 트래픽
양에서 나온다. 의미 있는 수익은 월 10만 PV 수준부터이며, 3~6개월은 수익이 거의 없다고
보아야 한다.

## 확장 전략: 단계형

세 가지 안을 검토했다.

- **A. 롱테일 폭격** — 지역 229개 × 대상 8종 조합으로 페이지 수천 개를 자동 생성.
  구글의 scaled content abuse 정책에 정면으로 걸린다. 채택하지 않는다.
- **B. 서비스 1건 = 페이지 1개, 7,500개 일괄 발행** — 신규 도메인이 하루에 수천 페이지를
  내놓으면 대량생성 신호다. 채택하지 않는다.
- **C. 단계형** — 채택.

단계형의 내용:

| 단계 | 규모 | 목표 |
|---|---|---|
| 1 | 80~120건 | AdSense 승인. 페이지당 자체 서술 800자 이상 |
| 2 | 주당 300~500건 | 승인 후 확장. 검수 통과분만 |
| 3 | 허브 확대 | 항목 5건 이상인 조합만 허브 페이지 생성 |

AdSense 승인은 페이지 수가 아니라 페이지 질로 갈린다. 승인 전에 대량 생성하면 계정이
막혀 재신청이 더 어려워진다.

## 아키텍처

### 스택

| 층 | 선택 | 비용 |
|---|---|---|
| 사이트 | Astro 5 정적 빌드 | 0 |
| 호스팅 | Cloudflare Pages | 0 (대역폭 무제한, 상업적 이용 허용) |
| 저장소 | GitHub public repo | 0 (Actions 시간 무제한) |
| 데이터 | data.go.kr 공공서비스 API | 0 |
| 자동화 | GitHub Actions cron | 0 (LLM 미사용) |
| 집필·검수 | 로컬 Claude Code 에이전트 | 0 (기존 구독 내) |

도메인은 `jiwongeum.pages.dev` 로 시작한다. 커스텀 도메인은 트래픽이 확인된 뒤에
붙이며, `src/lib/site.mjs` 의 `SITE.url` 한 줄과 `public/robots.txt` 만 바꾸면 된다.

### 데이터 흐름

```
data.go.kr API
   │  GitHub Actions, 매일 04:00 KST, LLM 없음
   ▼
data/raw/services.json         API 스냅샷
   │  scripts/normalize.mjs
   ▼
data/normalized/services.json  정규화 데이터
data/normalized/diff.json      이전 대비 신규/변경/종료
   │
   ├─ 변경 없음 → 종료
   └─ 변경 있음 → PR 자동 생성 (label: data-changed)
                     │  사람이 "업데이트" 실행
                     ▼
              에이전트 파이프라인 → content/services/*.md
                     │  Cloudflare Pages 자동 빌드
                     ▼
                  배포
```

핵심 분리 원칙: **`data/` 는 기계가 매일 덮어쓰는 영역, `content/` 는 글이 사는 영역.**
둘을 섞으면 동기화가 작성한 글을 지운다.

### 발행 게이트

`content/services/<id>.md` 의 프론트매터 `reviewed` 가 `true` 일 때만 페이지가 생성된다
(`src/pages/s/[id].astro` 의 `getStaticPaths`). 데이터만 있고 해설이 없는 페이지는 절대
만들어지지 않는다. 이것이 "가치 없는 콘텐츠" 판정을 구조적으로 막는 장치다.

허브 페이지는 소속 항목이 `MIN_HUB_ITEMS`(5) 이상일 때만 생성된다. 빈 조합 페이지가
doorway page 판정의 1순위이기 때문이다.

## 에이전트 구성

원칙: LLM 판단이 필요 없는 일은 에이전트로 만들지 않는다.

### 스크립트 (LLM 없음, Actions가 무인 실행)

| 파일 | 역할 |
|---|---|
| `scripts/sync.mjs` | API 전건 수집. `--probe` 로 응답 형태 확인 |
| `scripts/normalize.mjs` | 정규화 + 중복 제거 + 발행 가능 여부 판정 + 이전 대비 diff. 건수가 이전의 절반 이하로 줄면 API 장애로 보고 덮어쓰지 않는다 |
| `scripts/linkcheck.mjs` | 발행된 문서의 출처 링크 생존 확인. 죽으면 noindex |
| `scripts/lib.mjs` | 순수 함수 모음. `scripts/lib.test.mjs` 가 assert 로 검증 |
| `scripts/seed.mjs` | 개발용 샘플 데이터. 모든 항목에 `[샘플]` 표시 |

### 에이전트 (`.claude/agents/`)

| 이름 | 역할 | 거부권 |
|---|---|---|
| `scout` | 이번 회차 작업 대상 선정 → `queue.json` | — |
| `writer` | 해설 문서 작성 (`reviewed: false` 고정) | — |
| `fact-checker` | 원본과 1:1 대조. 숫자·기한·자격 검증 | 있음 |
| `policy-guard` | AdSense 정책 + 구글 스팸 정책 검사 | 있음 |
| `seo-editor` | 제목·설명 정리 후 `reviewed: true` 로 발행 | — |

`scout` 의 한계를 명시한다. 실제 검색량 데이터에 접근할 수 없으므로 초기에는
휴리스틱(대상 폭, 신청 기간 개방 여부, 데이터 충실도)으로 고른다. Search Console
데이터가 쌓이면 그것을 우선 근거로 전환한다.

### 파이프라인

```
sync + normalize → scout → [writer → fact-checker → policy-guard → seo-editor] → linkcheck → build
                                        ↓ FAIL           ↓ FAIL
                                    writer 재작업 (2회 연속 실패 시 사람 호출)
```

사용자 입력은 `업데이트` 한 마디. 상세 절차는 `CLAUDE.md` 에 있다.

## 페이지 구조

```
/                          홈
/s/<service-id>/           서비스 상세 — 수익 페이지
/target/<slug>/            대상 허브 8종
/region/                   지역 인덱스
/region/<sido>/            지역 허브 — 광역 16종 + 전국(national)
/guide/<slug>/             가이드 글 (사람이 작성)
/about /privacy /terms /contact /404
```

시군구 단위 허브는 1단계에서 만들지 않는다. 실제 데이터에서 시군구별 건수를 확인한
뒤, 5건 이상인 곳에만 추가한다.

### 서비스 상세 페이지 구성

빵부스러기 → H1 → 요약 박스(데이터) → 광고 → 본문 800자 이상(작성) → 광고 →
FAQ → 면책 문구 → 관련 지원금 5건 → 출처 링크와 기준일.

광고는 첫 화면을 덮지 않는다. 요약 박스 아래와 본문 아래에만 둔다.

### 구조화 데이터

| 페이지 | 스키마 |
|---|---|
| 서비스 상세 | `GovernmentService` + `BreadcrumbList` + `FAQPage` |
| 허브 | `CollectionPage` + `ItemList` |
| 가이드 | `Article` |
| 전 페이지 | `WebSite` + `Organization` |

### 색인 정책

신청이 종료된 제도와 출처 링크가 죽은 제도는 **페이지를 남기되** `noindex` 를 붙이고
사이트맵에서 제외한다. 삭제하면 404가 쌓이고, 다음 회차를 기다리는 방문자도 잃는다.

## AdSense 대응

### 승인 전 체크리스트

- 실질 콘텐츠 페이지 80건 이상, 각 자체 서술 800자 이상
- 개인정보처리방침에 쿠키·구글 광고·옵트아웃 링크 명시
- 이용약관, 소개, 문의 페이지
- 운영자 정보와 편집 원칙 공개 (E-E-A-T)
- 전 페이지 출처 링크 + 데이터 기준일
- 깨진 링크 0
- Search Console 등록, 30페이지 이상 색인 확인
- `public/ads.txt` 는 **승인 후에** 추가. 미리 만들면 검증에 실패한다

### 신청 순서

배포 → Search Console 등록 및 사이트맵 제출 → 2~3주 색인 대기(그동안 콘텐츠 추가) →
30페이지 이상 색인되면 신청 → 반려 시 사유를 `policy-guard` 규칙에 추가하고 2주 뒤 재신청.

1차 반려는 정상이다.

### 승인 후

`src/lib/site.mjs` 의 `SITE.adsenseClient` 에 `ca-pub-...` 를 넣으면 광고 스크립트와
`AdSlot` 컴포넌트가 자동으로 활성화된다. 값이 비어 있으면 아무것도 렌더링하지 않는다.

## 콘텐츠 원칙 (YMYL)

정부 지원금은 사람의 돈이 걸린 주제다. 구글은 이 영역에서 오정보에 특히 엄격하다.

1. 원본에 없는 숫자·기한·자격을 만들어내지 않는다. 모르면 "공고 확인".
2. 단정하지 않는다. "받습니다" 대신 "조건을 충족하면 신청할 수 있습니다".
3. 신청을 대행·중개하지 않으며, 개인정보를 수집하지 않는다.
4. 모든 페이지에 출처 원문 링크와 데이터 기준일을 표시한다.
5. 정정 요청 창구를 열어두고, 기관 담당자의 요청은 우선 처리한다.

## 알려진 제약

- **지역 분류 커버리지 92.5%.** 소관기관유형이 중앙행정기관·공공기관이면 전국,
  그 밖에는 기관명의 광역단체 정식 명칭으로 판정한다. 판정 불가 824건(대부분
  지방공기업·출연기관)은 지역을 비워 두고 지역 허브에서 제외한다. 축약형 매칭은
  하지 않는다 — `경기도 광주시` 가 광주광역시로 새는 사고가 실제로 있었다.
- **행정구역 변경 반영 필요.** 2026-08 기준 전남과 광주는 `전남광주통합특별시` 로
  통합되어 있다. 또 바뀌면 `src/lib/site.mjs` 의 `SIDO` 만 고친다.
- **Cloudflare Pages 파일 20,000개 제한.** 3단계에서 근접하면 Workers 정적 자산으로
  이전한다.
- **키워드 도구 접근 불가.** `scout` 은 초기에 휴리스틱으로 대상을 고른다.
